# Account recovery troubleshooting

Authentication logs on November 25 2026 showed one existing confirmed account, repeated signup HTTP 200, rejected password login, a successful recovery request and recorded mail.send, then HTTP 303 verification. This proves the service processed recovery, not inbox delivery or successful password change. Do not change an existing account's password on the owner's behalf or disable email confirmation.

The account screen now captures a recovery callback before the auth SDK clears it, shows a dedicated new-password/confirmation form only for verified recovery, and signs out locally on success so the customer signs in with the new password. A stale existing session cannot authorize the recovery form by itself. A homepage callback with Auth parameters is forwarded to the same-origin account route before the normal scripts run. Signup/recovery/resend messages are non-enumerating.

Owner configuration still required: check Supabase Authentication > URL Configuration. Set Site URL to https://burtonfound.timharmar.workers.dev and add exactly https://burtonfound.timharmar.workers.dev/account.html as an allowed redirect. For future custom domains, update both before switching. Do not use wildcard external URLs. Check Authentication > Email > SMTP Settings. Supabase default SMTP has restricted eligible recipients and low rate limits; use a verified custom SMTP sender for general customer registration and recovery. Do not turn off email confirmations. Test using a new mailbox that the owner controls, receive confirmation, click and sign in; then request one fresh reset, set a new password and sign in. A provider response cannot prove inbox delivery. No email was generated or sent by CI; fixture tests use a mocked SDK.
