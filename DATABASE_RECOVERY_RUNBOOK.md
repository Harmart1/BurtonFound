# Burton & Found recovery and backup plan

## What is automated
The weekly/on-demand GitHub Actions **synthetic database recovery drill** builds all repository migrations into a disposable PostgreSQL 17 container with minimal Auth and Storage fixtures, seeds fake inventory, account and paid-order records, makes a real custom-format PostgreSQL dump, restores it to another empty database and checks RLS, grants, paid inventory, overlapping bundle protection, and duplicate webhook handling. It uses no hosted connection or customer records, and uploads no database dump. This tests application schema recovery, not Supabase-managed Auth, file storage, provider settings or the actual production backup.

## Real backup — owner-only, private
Check [Supabase database backups](https://supabase.com/dashboard/project/nyvdrgpcwfasajyncnhi/database/backups) first; paid projects have provider daily backups and free projects should maintain off-site logical exports. Do not assume a backup exists without verifying the dashboard. No plan upgrade is authorized. Database backups do not contain Storage file contents. See the [current Supabase backup/restore instructions](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore).

A local helper, `scripts/local-encrypted-backup.py`, prepares the three documented Supabase CLI v3 logical exports and packages them into one age-encrypted archive, with an internal SHA-256 manifest. It intentionally refuses CI and output anywhere inside this public repository. It does not read service-role secrets or change hosted settings.

1. Install Python 3, current Supabase CLI v3, age, and Docker if required by CLI. Verify the CLI version and `supabase db dump --help` locally. On a trusted computer, create a private output directory on an encrypted local disk (e.g. BitLocker-protected Windows volume); never use a shared or synchronized plaintext directory.
2. Create an age key pair locally; keep the private identity offline in secure storage, with an independent recovery copy. Set environment variable BF_BACKUP_RECIPIENT to the public age1 recipient. Do not share the private key.
3. Obtain the project-specific direct or session-pooler connection URL (port 5432) from Supabase Connect. Supply BF_DB_URL locally via a password manager or trusted environment; do not paste in chat, GitHub, screenshots, or shell history. The local CLI receives the URL as a process argument, so run only on a trusted machine with no untrusted local users or process monitoring. No database password is needed by the GitHub drill.
4. From the repository, run `python scripts/local-encrypted-backup.py "D:/Private/BurtonFoundBackups"` (use your actual private directory). Temporary plaintext SQL is created only inside that protected directory, then removed; normal file deletion is not secure erasure. The helper does not verify the owner's ability to decrypt.
5. Decrypt on a trusted encrypted drive, verify all three checksums inside MANIFEST.sha256, and restore to an isolated test project or local Supabase environment using the official instructions. Never restore onto production for a test. Remove temporary plaintext afterward. Store only ciphertext in separately approved private off-site storage.
6. Copy Storage objects separately; record auth redirects, SMTP, project configuration, custom roles, environment secret names (not values), Cloudflare deployment and Stripe webhook settings. Preserve any encryption root key independently if the project uses Vault/encrypted columns, following Supabase guidance. Reconcile live payments and shipping state before reopening checkout after any real restore.

Suggested policy: daily verified private backup once accepting orders, weekly isolated recovery rehearsal, and a backup before migrations. The local helper is not scheduled by default. Set an owner-controlled scheduled task only after the first encrypted export and recovery key are verified. No actual hosted dump or external storage has been configured in this change.

## Restore gate
Keep checkout, live carrier rates and indexing off until the restored database is checked for orders, Stripe receipts/refunds, inventory holds, physical stock, private access policies, email and media. Never point the Worker at an unverified restore. Record backup date, destination, checksum verification, recovery result and responsible owner in a private record, not GitHub.
